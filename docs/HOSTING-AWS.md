# AWS S3 + CloudFront preparation

Prepared locally on 7 October 2026. No AWS resources, IAM users, certificates, DNS records or uploads were created. The generated template is reviewable infrastructure configuration; an AWS account deployment has not been tested.

## Architecture and artifacts

The AWS profile is for a site at the HTTPS domain root with clean URLs. Build for the exact eventual origin; `/about` has its own `about.html` rather than using an SPA homepage fallback. Repository subpaths and GitHub Pages directory URLs use their separate hosting profile.

```powershell
npm run build:aws -- --site-url=https://orbitengineering.com
```

This validates the public build in `dist/` and writes AWS infrastructure artifacts to `builds/aws-hosting/`. Replace the example origin with your final domain or generated CloudFront origin. For a non-indexable preview, append `--indexable=false`. The generic build also prepares AWS artifacts in `builds/generic-hosting/`.

`hosting/aws/generate.mjs` exports `generateAwsHosting({ manifest, redirects, outputDirectory })`. The production hosting generator supplies the completed SEO manifest and the shared legacy redirect list. It writes:

| File | Purpose |
| --- | --- |
| `cloudformation.json` | Private S3 bucket, CloudFront distribution/OAC, cache policies, response headers, route function and least-privilege bucket policy |
| `viewer-request.js` | Reviewable generated CloudFront runtime 2.0 function; `__CANONICAL_DOMAIN__` is replaced by the template's validated domain parameter |
| `upload-policy.example.json` | Example uploader permissions, with bucket/account/distribution placeholders; it does not create or attach IAM access |

Infrastructure files stay outside the public website payload. Only the verified public release files belong in S3. Use a short stack name, at most **45 characters**, because the template appends suffixes to CloudFront resource names. Use separate stack names and buckets for preview and production.

The bucket has public access blocked, ACLs disabled, default SSE-S3 encryption and versioning. CloudFront signs origin requests with OAC and reads the regular private S3 REST endpoint. Its read permission is restricted to this distribution's ARN. Requests to S3 over plain HTTP are denied. This follows [AWS's OAC guidance](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html); do not enable S3 website hosting or public-read ACLs.

CloudFront accepts `GET`/`HEAD`, redirects viewer HTTP to HTTPS, rejects private/source/executable paths, and permanently redirects the 22 legacy paths. Known routes map to their individual generated HTML files. Missing S3 objects return the branded `404.html` with HTTP **404**, including S3's missing-object **403** response. There is no `403/404 → index.html → 200` fallback. [AWS documents the custom error-page flow](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/HTTPStatusCodes.html).

Encoded spaces in public asset filenames remain supported, including canonical-host redirects. Control characters, encoded separators and paths containing a decoded percent sign are rejected. Avoid literal `%` in future public filenames; use ordinary safe names or spaces encoded as `%20`.

The shared CSP and nine security headers are applied by CloudFront response policies and also included on responses generated by the route function. HTML and unhashed public files revalidate. Real hashed assets receive immutable S3 metadata during the upload below; the asset response policy preserves that origin header and uses a revalidation fallback when absent. It does not force a year-long browser cache onto missing assets. CloudFront's HTML cache is disabled, so a newly uploaded HTML object is available without a stale CDN copy. Its asset edge cache can retain successful objects independently of browser headers; custom error TTL is zero. Query strings and cookies are excluded from the static object cache key. Redirects preserve query parameters. See [AWS response-header and browser-cache behavior](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/modifying-response-headers.html). Verify missing assets at the deployed edge as well as successful images/scripts.

## Domain, TLS and SEO decisions

For your custom domain, provide `CanonicalDomain` as the hostname only, for example `orbitengineering.com`. `AlternateDomain` can be `www.orbitengineering.com`; the issued certificate must cover both names. `CertificateArn` must refer to ACM in **us-east-1**, regardless of the S3 stack's region. The custom-domain distribution uses SNI and a TLS 1.2 minimum policy. Validate the certificate's ownership records first. [AWS's certificate requirements](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cnames-and-https-requirements.html) explain the regional requirement.

Leaving both domain and certificate parameters empty uses the generated `*.cloudfront.net` URL and its AWS certificate. The function then performs route redirects relative to the same host. That generated URL is unknown before stack creation: create the infrastructure first, read the `SiteUrl` output, **rebuild for that exact HTTPS origin**, then upload. The template's `BuildOrigin` output is the origin embedded in the current files; it must match the intended published origin. For private review, use the project's non-indexable build option; the AWS profile also emits `X-Robots-Tag: noindex, follow` for that build. A robots restriction alone is not authentication.

For a custom domain, configure DNS to the CloudFront distribution only after uploading and validating the release. A Route 53 alias or another provider's supported CNAME/ALIAS arrangement depends on your DNS provider. This template deliberately does not change DNS or request certificates.

`WebAclArn` optionally attaches an existing CloudFront-scope AWS WAFv2 Web ACL. It does not create WAF rules, rate limits, access logs or account alerts. Choose and review those account settings before launch if needed; they can introduce cost and retain visitors' IP addresses. Set an AWS billing budget and use MFA/short-lived role credentials for administrators.

## Later deployment procedure

These commands are instructions for a later authorized deployment. They have **not** been run. Replace every `REPLACE_*` value, and use the actual generated artifact and verified public-payload paths from the release report. Authenticate using IAM Identity Center or a short-lived deployment role; never put AWS keys in frontend `VITE_*` variables or commit credentials.

1. Build the AWS profile for the final origin and run the project's production checks. Review the resulting manifest, hashes, canonical URLs and infrastructure template. Keep the previous release for rollback.
2. If the AWS CLI is installed and authenticated, validate the template against AWS before a CloudFormation change set:

   ```powershell
   aws cloudformation validate-template --template-body file://REPLACE_ARTIFACT_PATH/cloudformation.json --region REPLACE_REGION
   ```

   The file is self-contained. Create and review a change set using the AWS console or CLI; creating/executing it is a separate deployment action. For a custom domain, pass the certificate/domain parameters. For the generated CloudFront domain, leave them empty and rebuild after reading the stack output. Check CloudFront deployment reaches `Deployed` and the bucket remains private.

3. Attach an appropriately scoped upload role using the example policy with real identifiers. The example permits upload/list and invalidation only; it grants no public ACL, bucket-policy change, IAM creation or object deletion. Add object deletion only if a separate reviewed cleanup operation needs it. Bucket versioning retains earlier objects; plan retention and lifecycle cost with the account owner.
4. Upload hashed assets **first**, preserving old hashes for rollback and cached pages. Then upload the other verified public files. Do not upload the repository, `node_modules`, `.env`, source, generated infrastructure files or old CMS files. The following excludes Apache/IIS configuration from S3:

   ```powershell
   aws s3 cp REPLACE_PUBLIC_PAYLOAD/assets/ s3://REPLACE_BUCKET/assets/ --recursive --cache-control 'public, max-age=31536000, immutable' --only-show-errors
   aws s3 cp REPLACE_PUBLIC_PAYLOAD/ s3://REPLACE_BUCKET/ --recursive --exclude 'assets/*' --exclude '.htaccess' --exclude 'web.config' --cache-control 'no-cache, max-age=0, must-revalidate' --only-show-errors
   ```

   The CLI normally guesses each object's Content-Type. Verify HTML is `text/html`, JS is JavaScript, CSS is `text/css`, images have their real MIME type, and `robots.txt` is text. `nosniff` makes incorrect types visible rather than silently treating them as executable content. Do not add `--acl public-read` or blindly use `sync --delete` against the versioned bucket.
5. After any policy/function update, wait for CloudFront deployment. If an invalidation is required, scope it to this distribution:

   ```powershell
   aws cloudfront create-invalidation --distribution-id REPLACE_DISTRIBUTION_ID --paths '/*'
   ```

6. Verify the HTTPS site before switching DNS: homepage plus all 35 deep URLs load directly and on refresh; `/page/profile` permanently redirects to `/about`; `/does-not-exist` returns a branded **404**; `/.env` is rejected; HTTP redirects to HTTPS; the configured alias redirects to the canonical host; the nine response headers and MIME types appear; sitemap/robots/canonicals contain only the final intended origin. Check navigation, forms, maps, typography and images on mobile too. The enquiry flow opens user-controlled WhatsApp/email drafts and does not require an AWS backend.
7. Verify the same checks through the final domain after DNS and TLS are active. Keep the prior HTML and old hashed assets available for rollback. To revert, restore the previous verified payload/version and previous infrastructure configuration; do not delete the bucket.

## Verification boundaries

Run the local AWS checks with:

```powershell
node hosting/aws/verify.mjs
```

The checker executes the emitted route function in an isolated Node VM and checks every route, both methods, legacy redirects, queries, malformed/private paths, canonical aliases, cache settings and private-bucket/OAC configuration. The current function is approximately 7.5 KB, below [CloudFront's fixed 10 KB limit](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cloudfront-limits.html), and emits plain JavaScript supported by [CloudFront runtime 2.0](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/functions-javascript-runtime-20.html). Generation fails if that limit or the native CSP-header quota is exceeded. A Node VM check does not prove CloudFront compute utilization, certificate eligibility, AWS permissions or deployed HTTP behavior: run AWS's function test/CloudFormation validation and the live checks when you choose to deploy.
